# 基于 Vibe Coding 的 Git 提交 AI Agent 代码审查与风险分析系统 — 技术实现方案与项目报告书

> **技术栈基线（2026-09 优化版）**：全栈 TypeScript（6.x）· React 19 · Vite 8（Rolldown 内核）· pnpm 10 Monorepo · Turborepo · Node.js 22 LTS · Hono 4 · LangGraph.js
> 本次优化将原 Python/Node 混合栈统一为**前后端全 TypeScript 单语言栈**，并重新确认了核心业务链路（详见 3.0 节）。

## 第一部分：技术实现方案

### 一、项目背景与设计理念

#### 1.1 Vibe Coding 在 2026 年的工程化演进

Vibe Coding 在 2026 年已从"凭感觉让 AI 写代码"演变为结构化的 AI 优先开发方法论。其核心工作流是 Prompt → Generate → Review → Refine 四阶段循环，其中 Review 和 Refine 阶段消耗了最多的人力投入，也是价值最高的环节。在这一范式下，开发者的角色从逐行编码者转变为架构师和审查者，代码审查的方式也从"逐行阅读"变为"审查 diff 变更 + 核心逻辑校验"。

本项目的核心理念正是将 Vibe Coding 工作流中的 Review 阶段自动化、智能化：当开发者执行 `git commit` 时，AI Agent 自动对暂存区的代码变更进行审查，识别缺陷、评估风险，并输出结构化报告，在代码进入仓库之前就完成第一轮质量把关。

#### 1.2 当前代码审查的核心痛点

当前代码审查的核心痛点
传统代码审查面临以下关键挑战：

**人工审查的瓶颈**：人工审查在速度和一致性上存在明显瓶颈，审查质量高度依赖审查者的经验和精力。一个包含 500 行变更的 PR 可能需要数十分钟的人工审查。

**静态分析工具的局限**：传统 SAST 工具（如 CodeQL、Snyk）在漏洞检测上的平均 F1 分数仅为 0.260~~0.546，而基于 LLM 的扫描工具 F1 分数可达 0.750~~0.797。静态分析工具受限于规则匹配，难以理解代码语义和业务逻辑。

**LLM 审查的幻觉问题**：GenAI 代码审查工具的平均幻觉率为 18%，没有工具在注入类漏洞上达到 70% 的召回率。关键在于将 LLM 的判断与确定性分析工具结合，降低误报。

**上下文不足导致的漏报**：业务逻辑类漏洞（如权限校验缺失）的平均召回率仅为 21%，但当为 LLM 提供约 2000 token 的项目背景描述后，召回率可提升至 51%。这证实了 RAG 知识库在代码审查中的必要性。

#### 1.3 设计原则

本项目的核心理念正是将 Vibe Coding 工作流中的 Review 阶段自动化、智能化：当开发者执行 `git commit` 时，AI Agent 自动对暂存区的代码变更进行审查，识别缺陷、评估风险，并输出结构化报告，在代码进入仓库之前就完成第一轮质量把关。

- **混合分析原则**：LLM 语义理解与静态分析工具互补，通过交叉验证降低误报和幻觉。
- **增量审查原则**：仅审查 diff 变更内容，而非全量代码，以 AgenticSCR 的 diff-centric 范式为基础。
- **确定性优先原则**：确定性工具能判定的问题（如语法错误、复杂度超标）不交给 LLM，减少 token 浪费和不确定性。
- **可审计原则**：每次审查的输入、推理过程、工具调用和输出均完整记录，支持事后追溯。

#### 1.4 全栈 TypeScript 单语言栈的选型理由

本项目将 Git Hook 运行器、Agent 编排、API Server、Web Dashboard、MCP 工具全部统一到 TypeScript，理由如下：

1. **单语言降低认知与维护成本**：从 Git Hook 的 Node 运行器，到编排引擎，再到 Dashboard 前端，全链路一种语言、一套工具链（pnpm + Turborepo 统一管理），避免了原方案 Python/Node 双栈带来的进程调用、序列化边界和双重依赖维护。
2. **AI/Agent 生态的 TypeScript 一等公民地位**：Model Context Protocol 官方 SDK（`@modelcontextprotocol/sdk`）、Vercel AI SDK 5（统一 LLM Provider、内置工具调用循环与流式输出）均以 TypeScript 优先发布，本项目的两大核心依赖无需任何跨语言桥接。
3. **端到端类型安全**：以 zod schema 为单一事实源，配置校验 → API 契约 → 数据库行类型 → 前端表单全链路推导自同一份定义，契约漂移在编译期即被发现。
4. **分发与跨平台优势**：产物为纯 Node.js 包与静态前端，无 Python 解释器/虚拟环境碎片化问题；对 Windows、macOS、Linux 一致支持——这对 Git Hook 场景尤为重要（团队成员操作系统各异）。
5. **代码分析主战场即 JS/TS**：`ts-morph`、`oxc-parser` 对 JS/TS 提供第一方 AST 能力；其他语言（Python/Go/Java）通过 Tree-sitter 语法包覆盖。

#### 2.1 各层职责

**交互层**：提供多种触发入口。Web Dashboard 是主入口（React 19 + Vite 8：发起审查、审查历史、diff 视图、统计分析与配置管理）；Git Hook 在 `pre-commit` 阶段经 Node 运行器自动触发审查；API Server 基于 Hono 4，对 Hook/CI 提供同步审查端点，并通过 SSE 向 Dashboard 推送实时审查进度；IDE Plugin（可选，Phase 4）提供开发时的实时反馈。

**Agent 编排层**：基于 LangGraph.js（`@langchain/langgraph`，官方 1.0 稳定版）的 StateGraph 编排引擎，定义审查流水线的各个节点及其依赖关系。共享状态以 Channel/Reducer 模型声明（`Annotation.Root`），每个节点只返回增量更新，由 reducer 自动合并——并行审查分支的结果合并因此无需手写。编排层能力与业务需求一一对应：条件边实现自愈回退、fan-out/fan-in 实现三 Agent 并行、checkpointer 提供可审计的状态快照与断点恢复（直接兑现"可审计原则"）、`graph.stream()` 的节点级事件直通 API Server 的 SSE 实时进度。分工边界：LangGraph 负责"流程编排"，AI SDK 负责"单步 LLM 调用与工具循环"，互不重叠。

**分析引擎层**：包含四类分析引擎——LLM Agent（基于 AI SDK 5 的 ReAct 循环语义审查）、静态分析器（Tree-sitter 多语言 AST 解析 + ts-morph/oxc 的 JS/TS 深度分析 + Semgrep 规则扫描）、RAG 知识库（LanceDB 嵌入式向量检索 + MiniSearch BM25 混合召回）、测试沙箱（Docker 隔离的验证环境，Phase 4）。工具默认以进程内函数调用（In-Process Tool Bus）暴露，性能最优；同时通过 MCP 协议（stdio/SSE）对外暴露同一套工具，供第三方 Agent（如 Claude Code）即插即用。

**数据层**：SQLite（默认）/ PostgreSQL（团队版）经 Drizzle ORM 双方言同构访问，存储审查记录和配置；LanceDB 为**嵌入式**向量数据库（npm 原生绑定，随应用进程运行，无需独立服务），存储代码语义索引；Redis 用于团队版的缓存和任务队列（单机版以 SQLite 表降级实现）；文件系统存储 Markdown/HTML 报告；prom-client 暴露 Prometheus 指标。

### 三、核心模块详细设计

#### 3.0 核心业务链路总览（已确认）

审查流水线的完整业务链路如下，本方案对其逐环节做了确认与修正（关键修正见括号标注）：

1. **触发**：开发者执行 `git commit` → pre-commit hook 调用 `POST /api/hooks/review`（默认 **fast 模式**，控制提交等待时间）；也可在 Web 上手动发起（默认审查暂存区）。
2. **Diff 解析**：pre-commit 阶段读取**暂存区（index）快照**而非工作区文件——工作区可能包含未暂存改动，只有 index 内容才与本次 commit 一致（**关键正确性修正**）；Web/CI 亦可显式选择工作区、单个提交或提交区间。基于 diff 构建函数级上下文包。
3. **风险规划**：Risk Planner 对每个变更文件评分分流：≥60 深度 LLM 审查、40~60 快速 LLM 审查、<40 仅静态分析。
4. **并行审查**：正确性、安全、性能三个审查 Agent 经 LangGraph fan-out 三路并行执行（受 `review.dimensions` 约束，关闭的维度不调用 Provider），ReAct 循环中按需调用工具，全程受 token 预算器与取消信号约束。
5. **交叉验证**：5 阶段后处理（严重度重分类 → 置信度评分 → 跨文件分析 → 自动修复建议 → 去重排序）抑制幻觉（当前实现阶段 1/2/5，其余见 `docs/审查流程评估.md` 的技术债清单）。
6. **自愈回退**：BLOCKER 级发现置信度 < 0.6 时，携带上下文重审，最多 3 轮；每轮受 token 预算与并发上限约束。
7. **报告与决策**：生成五段式 Markdown/JSON/HTML 报告（记录 commit 与作者），按 `blockOn` 阈值决定 `exitCode`（0 放行 / 1 阻断提交）。
8. **落库与推送**：结果经缓存层（内容哈希去重）写入 SQLite，并通过 SSE 实时推送 Dashboard；Hook/CI 同步等待退出码，CI 模式下自动发表 PR 评论。

**fast / full 双模式定义**（确认的核心业务参数）：

| 环节         | fast（pre-commit 默认）                | full（CI / 手动 `--mode full`） |
| ------------ | -------------------------------------- | ------------------------------- |
| 静态分析     | 全部执行（确定性、低开销）             | 全部执行                        |
| LLM 深度审查 | 仅风险分 ≥60 文件，正确性 + 安全两维度 | 所有 deep 文件，四维度全开      |
| RAG 检索     | 仅高风险文件注入                       | 全部文件注入                    |
| 交叉验证     | 简化（去重 + 置信度过滤）              | 完整 5 阶段 + 3 轮自愈回退      |
| 目标耗时     | ≤ 15s（500 行变更）                    | ≤ 60s（500 行变更）             |

#### 3.1 Diff 解析与上下文提取模块

这是整个审查流水线的入口。Git diff 提供了行级别的变更信息，但缺少语义上下文。本模块在 Git 原生 diff 的基础上，构建结构化的、AI 就绪的代码上下文包。

```typescript
// packages/diff/src/context-builder.ts
import { execFile } from 'node:child_process';
import { promisify } from 'node:util';
import { pMap } from 'p-map';
import { parseUnifiedDiff } from './parser'; // unified diff 解析（封装 parse-git-diff）
import { extractEnclosingFunctions, extractAstSignature } from './ast'; // Tree-sitter
import { isMeaningfulChange, classifyChange } from './filter';
import type {
  CodeContext,
  FileContext,
  FileDiff,
  GitRunner,
  RagRetriever,
  IgnoreRules,
} from '@ai-review/shared';

const exec = promisify(execFile);

export class DiffContextBuilder {
  constructor(
    private readonly repoPath: string,
    private readonly rag: RagRetriever,
    private readonly ignores: IgnoreRules,
    private readonly contextRadius: number = 50,
  ) {}

  /**
   * 核心正确性约定：审查对象是暂存区（index）快照，而不是工作区。
   * pre-commit 阶段工作区可能包含未暂存改动，只有 index 内容才与本次 commit 一致。
   * 采用 git show :path 只读 index blob，不使用 git stash --keep-index 等会改动工作区的方案。
   */
  async build(): Promise<CodeContext> {
    const git: GitRunner = async (...args: string[]) =>
      (await exec('git', args, { cwd: this.repoPath, maxBuffer: 64 * 1024 * 1024 })).stdout;

    // 1. 读取暂存区 diff，扩大 unified 上下文到 ±N 行，便于后续函数级理解
    const stagedDiff = await git('diff', '--cached', `--unified=${this.contextRadius}`);

    // 2. 解析 unified diff，提取变更文件与行范围
    const fileDiffs: FileDiff[] = parseUnifiedDiff(stagedDiff);

    // 3. 过滤：二进制文件、纯空白变更、命中 ignore 规则的文件（锁文件/构建产物等）
    const meaningful = fileDiffs.filter(
      (d) => !d.binary && this.ignores.allows(d.path) && isMeaningfulChange(d),
    );

    // 4. 按文件构建上下文包（I/O 并行，限流防止大提交打爆 git 进程）
    const contexts = await pMap(meaningful, (d) => this.buildFileContext(d, git), {
      concurrency: 8,
    });

    return { files: contexts, metadata: this.buildMetadata(contexts) };
  }

  private async buildFileContext(diff: FileDiff, git: GitRunner): Promise<FileContext> {
    // 4a. 从 index 读取文件完整内容（新增文件 index 中已有 blob；删除文件降级为仅 diff 审查）
    const stagedContent = await git('show', `:${diff.path}`).catch(() => '');

    // 4b. Tree-sitter 定位变更行所在函数/类，提取完整源码与 AST 签名（非仅 diff 行）
    const snippet = extractEnclosingFunctions(stagedContent, diff.changedLines, this.contextRadius);
    const signature = extractAstSignature(snippet);

    // 4c. RAG 检索：以变更摘要为查询，召回相似实现、项目约定与历史修复记录
    const ragHits = await this.rag.query({
      query: diff.summary,
      topK: 5,
      filter: { path: diff.path },
    });

    return { diff, snippet, signature, ragHits, changeType: classifyChange(diff) };
  }
}
```

**关键设计决策**：

- **以 index 为唯一事实源**：`git show :path` 直接读取暂存区 blob，保证"审查的内容 = 提交的内容"，杜绝工作区未暂存改动混入审查造成的误判。
- **上下文半径可配置**：默认提取变更行前后 50 行的代码，足以覆盖大多数函数的完整逻辑，同时控制 token 消耗；Tree-sitter 的函数边界裁剪进一步去除无关代码。
- **忽略删除行**：AI 审查聚焦于新增/修改的代码；删除操作由确定性工具处理（如检测是否删除了必要的错误处理——该信号同时供 Risk Planner 加权）。
- **RAG 检索以变更摘要为查询**：利用 diff 的变更摘要（由小模型快速生成或从 commit message 提取）作为向量检索的查询，召回相关的历史修复和项目约定。

#### 3.2 风险规划器（Risk Planner）

在 LLM 审查之前，风险规划器对变更文件进行优先级排序，将 LLM 的注意力集中在高风险区域，减少 token 浪费。这是确定性规划器（Deterministic Planner）模式的具体实现。

**风险评估规则**：

| 维度     | 低风险               | 中风险             | 高风险                    |
| -------- | -------------------- | ------------------ | ------------------------- |
| 文件类型 | 测试文件、文档       | 工具函数、配置文件 | 认证/授权、支付、数据访问 |
| 变更规模 | < 10 行              | 10-100 行          | > 100 行                  |
| 变更类型 | 格式调整             | 新功能             | 逻辑修改、删除错误处理    |
| 文件历史 | 稳定（> 6 月无修改） | 偶发修改           | 高频修改（> 5 次/月）     |

每个文件获得 0-100 的风险分数，分数 ≥ 60 的文件进入深度 LLM 审查，40-60 的文件进入快速审查，< 40 的文件仅运行静态分析。

```typescript
// packages/core/src/risk-planner.ts
import type { FileDiff, FileHistory } from '@ai-review/shared';

/** 高风险路径特征：认证、支付、数据访问等（大小写不敏感） */
const HIGH_RISK_PATTERNS: RegExp[] = [
  /auth/,
  /login/,
  /password/,
  /token/,
  /secret/,
  /permission/,
  /payment/,
  /billing/,
  /admin/,
  /sql/,
  /query/,
  /execute/,
  /eval/,
];

/** 删除行中的高风险信号：移除错误处理/校验是典型危险变更 */
const REMOVED_GUARD_PATTERNS: RegExp[] = [
  /\b(try|except|catch|finally|rollback)\b/,
  /\b(validate|sanitize|escape|checkPermission|requireUser)\b/,
];

export interface ScoredFile {
  diff: FileDiff;
  score: number;
}
export interface ReviewPlan {
  deep: ScoredFile[];
  quick: ScoredFile[];
  staticOnly: ScoredFile[];
}

export class RiskPlanner {
  constructor(private readonly history: FileHistory) {}

  async plan(diffs: FileDiff[]): Promise<ReviewPlan> {
    const scored: ScoredFile[] = [];

    for (const diff of diffs) {
      let score = 0;
      const path = diff.path.toLowerCase();

      // ① 路径风险：命中认证/支付等敏感路径 +30
      if (HIGH_RISK_PATTERNS.some((p) => p.test(path))) score += 30;

      // ② 变更规模
      const changed = diff.additions + diff.deletions;
      if (changed > 100) score += 25;
      else if (changed > 30) score += 15;

      // ③ 删除守卫逻辑 +20（删除错误处理是高风险信号）
      if (diff.removedLines.some((line) => REMOVED_GUARD_PATTERNS.test(line))) score += 20;

      // ④ 文件热度：近 30 天修改次数 > 5 +15
      if ((await this.history.changeFrequency(diff.path, 30)) > 5) score += 15;

      // ⑤ 测试/文档/纯格式化降权
      if (isTestOrDocs(path) || isFormattingOnly(diff)) score = Math.max(0, score - 25);

      scored.push({ diff, score: Math.min(score, 100) });
    }

    scored.sort((a, b) => b.score - a.score);
    return {
      deep: scored.filter((s) => s.score >= 60), // 深度 LLM 审查（全维度）
      quick: scored.filter((s) => s.score >= 40 && s.score < 60), // 快速 LLM 审查（单维度）
      staticOnly: scored.filter((s) => s.score < 40), // 仅静态分析，不消耗 LLM token
    };
  }
}
```

#### 3.3 多 Agent 并行审查引擎

审查引擎采用多 Agent 并行架构，三个审查 Agent 分别从不同维度独立分析代码，避免"三个 Reviewer 审同一批代码——都审不深"的问题。

**Agent 1：正确性与逻辑审查 Agent**

职责：检测逻辑错误、边界条件缺失、异常处理遗漏、并发安全问题。

System Prompt 设计要点：

```
你是一位资深代码审查专家，专注于代码正确性和逻辑缺陷检测。

审查规则：
- 检查边界条件：空值、越界、除零、类型转换异常
- 检查异常处理：是否正确捕获并处理异常，是否存在静默失败
- 检查并发安全：共享状态是否有竞态条件，锁的粒度是否合理
- 检查资源管理：文件/连接/内存是否正确释放
- 检查返回值：所有代码路径是否都有合理的返回值

输出格式：每个问题必须包含 [严重度] [文件:行号] [问题描述] [修复建议]
严重度分级：BLOCKER / WARNING / NIT / PRAISE

禁止行为：
- 不要对不确定的问题编造具体的修复代码
- 不要报告纯风格问题（由其他 Agent 处理）
- 如果无法确定问题是否真实存在，标记为 LOW_CONFIDENCE
```

**Agent 2：安全与风险审查 Agent**

职责：检测安全漏洞、敏感信息泄露、依赖风险、权限问题。

覆盖的漏洞类型参考 CWE 分类，重点覆盖注入类（CWE-89/79）、认证授权类（CWE-287/862）、敏感数据暴露（CWE-200/798）、不安全反序列化（CWE-502）等。

**Agent 3：性能与可维护性审查 Agent**

职责：检测性能反模式、代码复杂度、可维护性问题。

检测项包括：N+1 查询、不必要的循环嵌套、缺失索引提示、过长函数（> 50 行）、过深嵌套（> 4 层）、魔法数字、重复代码块。

**并行执行与资源约束**：


**Token 预算器**：全流水线共享一个预算实例，耗尽时未审查的低优先级文件自动降级为 `staticOnly`，并在报告中标注"预算受限，已降级"，保证审查成本有硬上限：

```typescript
// packages/llm/src/budget.ts
export class TokenBudget {
  private used = 0;
  constructor(
    private readonly max: number,
    private readonly onExhausted?: () => void,
  ) {}

  tryReserve(estimate: number): boolean {
    if (this.used + estimate > this.max) {
      this.onExhausted?.();
      return false;
    }
    return true;
  }

  account(usage: { totalTokens: number }): void {
    this.used += usage.totalTokens;
  }
  get usageRatio(): number {
    return this.used / this.max;
  }
}
```

#### 3.4 静态分析集成层

静态分析层通过工具总线（默认进程内调用，对外经 MCP 协议暴露）供 Agent 在 ReAct 循环中按需调用。

**核心工具清单**：

| 工具               | 功能         | 输入      | 输出                    |
| ------------------ | ------------ | --------- | ----------------------- |
| `ast_parse`        | AST 解析     | 文件路径  | 函数/类列表、复杂度指标 |
| `complexity_check` | 圈复杂度计算 | 文件路径  | 超标函数列表            |
| `dependency_scan`  | 依赖漏洞扫描 | 依赖文件  | CVE 列表 + 严重度       |
| `secret_scan`      | 敏感信息检测 | diff 文本 | 疑似密钥/Token 列表     |
| `test_impact`      | 测试影响分析 | 变更文件  | 受影响的测试用例列表    |
| `call_graph`       | 调用图构建   | 函数名    | 调用链和依赖关系        |

**JS/TS 圈复杂度分析**（ts-morph 实现，与本项目技术栈同构；Python/Go/Java 走 Tree-sitter 语法包，JS/TS 亦可切换 oxc-parser 获得数量级解析提速）：

```typescript
// packages/tools/src/complexity.ts
import { Project, Node, SyntaxKind } from 'ts-morph';

export interface FunctionMetrics {
  name: string;
  line: number;
  complexity: number; // 1 + 分支/循环/异常/短路表达式节点数
  params: string[];
  isAsync: boolean;
}

const DECISION_KINDS = [
  SyntaxKind.IfStatement,
  SyntaxKind.ForStatement,
  SyntaxKind.ForOfStatement,
  SyntaxKind.ForInStatement,
  SyntaxKind.WhileStatement,
  SyntaxKind.DoStatement,
  SyntaxKind.CatchClause,
  SyntaxKind.CaseClause,
  SyntaxKind.ConditionalExpression,
];

export function analyzeComplexity(source: string, threshold = 15): FunctionMetrics[] {
  const project = new Project({ useInMemoryFileSystem: true });
  const file = project.createSourceFile('reviewed.ts', source);
  const functions = [
    ...file.getDescendantsOfKind(SyntaxKind.FunctionDeclaration),
    ...file.getDescendantsOfKind(SyntaxKind.MethodDeclaration),
    ...file.getDescendantsOfKind(SyntaxKind.ArrowFunction),
  ];

  return functions
    .map((fn) => {
      let complexity = 1;
      for (const node of fn.getDescendants()) {
        if (DECISION_KINDS.includes(node.getKind())) complexity++;
        if (Node.isBinaryExpression(node)) {
          const op = node.getOperatorToken().getKind();
          if (
            op === SyntaxKind.AmpersandAmpersandToken ||
            op === SyntaxKind.BarBarToken ||
            op === SyntaxKind.QuestionQuestionToken
          )
            complexity++;
        }
      }
      return {
        name: fn.getName() ?? '(anonymous)',
        line: fn.getStartLineNumber(),
        complexity,
        params: fn.getParameters().map((p) => p.getName()),
        isAsync: fn.isAsync(),
      };
    })
    .filter((m) => m.complexity >= threshold);
}
```

#### 3.5 RAG 知识库模块

RAG 知识库为 LLM 审查提供项目上下文，有效提升业务逻辑类问题的召回率。根据 Google SECL 基准测试，约 2000 token 的项目背景信息可使逻辑漏洞召回率提升约 2 倍。

**知识库构建流程**：

1. **代码索引**：基于 Tree-sitter 在函数/类边界切分代码，使用 AI SDK 的 `embedMany`（云端 `text-embedding-3-large` 或本地 Ollama `nomic-embed-text`）生成向量，存入 LanceDB（嵌入式，随项目 `.ai-review-cache/` 目录持久化，零外部服务依赖）。
2. **项目文档索引**：将 `README.md`、`CLAUDE.md`、架构文档、API 规范等向量化存储。
3. **历史记录索引**：将历史审查报告、修复 commit 的 message 向量化，供检索相似问题的历史处理方式。

**检索策略**：采用 BM25（MiniSearch 内存倒排索引）+ 余弦相似度的混合检索，通过倒数排名融合（RRF）合并结果。对于代码变更，检索三类上下文——同一文件的相似函数（理解编码风格）、项目中的相似模式（理解架构约定）、相关文档（理解业务规则）。

```typescript
// packages/rag/src/knowledge-base.ts
import * as lancedb from '@lancedb/lancedb';
import MiniSearch from 'minisearch';
import { embed, embedMany } from 'ai';
import type { EmbeddingModel } from 'ai';
import { chunkByAst } from './chunker';
import { rrfFuse } from './fusion';
import type { RagQuery, RagHit, Chunk } from '@ai-review/shared';

export class KnowledgeBase {
  private table?: lancedb.Table;
  private bm25 = new MiniSearch({ fields: ['text'], storeFields: ['id', 'path', 'kind'] });

  constructor(
    private readonly indexDir: string,
    private readonly embeddingModel: EmbeddingModel<string>,
  ) {}

  async build(paths: string[]): Promise<void> {
    // 1. 按 AST 边界切块（函数/类），代码/文档/历史报告分别入库
    const chunks: Chunk[] = await chunkByAst(paths);

    // 2. 批量向量化（AI SDK 自动分批与重试）
    const { embeddings } = await embedMany({
      model: this.embeddingModel,
      values: chunks.map((c) => c.text),
    });

    // 3. 写入 LanceDB（嵌入式，本地目录持久化）并同步构建 BM25 索引
    const db = await lancedb.connect(this.indexDir);
    this.table = await db.createTable(
      'chunks',
      chunks.map((c, i) => ({ ...c, vector: embeddings[i] })),
      { mode: 'overwrite' },
    );
    this.bm25.addAll(chunks.map((c) => ({ id: c.id, text: c.text, path: c.path, kind: c.kind })));
  }

  async query({ query, topK = 5, filter }: RagQuery): Promise<RagHit[]> {
    const [{ embedding: qvec }, bm25Hits] = await Promise.all([
      embed({ model: this.embeddingModel, value: query }),
      Promise.resolve(this.bm25.search(query).slice(0, topK * 3)),
    ]);

    const vecHits = await this.table!.search(qvec)
      .limit(topK * 3)
      .execute();

    // 倒数排名融合（RRF）：合并向量召回与 BM25 召回
    return rrfFuse(vecHits, bm25Hits, topK, filter);
  }
}
```

**增量索引**：以文件内容哈希为键做差量更新，仅在文件变更时重新切块与向量化；大型仓库首次索引耗时问题由此缓解。

#### 3.6 交叉验证与幻觉抑制模块

这是降低 LLM 幻觉率的关键模块，在 LLM 审查结束后进行 5 阶段后处理：

**阶段 1：严重度重分类**。使用规则数据库对 LLM 标记的严重度进行校正。例如，LLM 将测试文件中的硬编码标记为 BLOCKER，规则库会降级为 NIT。

**阶段 2：置信度评分**。每个发现获得 0-1 的置信度分数，基于：工具类型基础分（静态分析 0.9，LLM 语义 0.6）、是否有多源交叉确认（+0.2）、问题模式的已知误报率（调整）。

**阶段 3：跨文件分析**。检测 LLM 容易遗漏的跨文件问题——缺失测试覆盖（新函数无对应测试）、过时 import（引用了已删除的模块）、API 契约破坏（函数签名变更但调用方未更新）。本阶段大量借助 TypeScript 工具链能力：对 TS 项目直接用 ts-morph 做"签名变更 vs 调用方"的编译级核对，结论是确定性的。

**阶段 4：自动修复建议**。对匹配常见 linter 规则的问题（如未使用的 import、空 catch 块），复用 ESLint 规则元数据自动生成修复代码。

**阶段 5：去重与排序**。合并多个 Agent 的重复发现（按文件 + 行区间 + 问题类别聚类），按"严重度 × 置信度"排序。

**幻觉抑制策略**：

- **断言校验**：如果 LLM 声称某处存在 SQL 注入，但静态分析未检测到任何污点传播路径，则将置信度降为 LOW。
- **CVE 校验**：如果 LLM 引用了 CVE 编号，必须通过外部 API 验证其真实性，无法验证的 CVE 引用直接移除。
- **上下文约束**：在 System Prompt 中明确要求"不确定的问题标记为 LOW_CONFIDENCE 而非编造修复方案"。
- **结构化输出校验**：LLM 输出必须通过 zod schema 解析（文件存在、行号在 diff 范围内、字段类型正确），解析失败的发现整条丢弃并计入自愈触发条件。

#### 3.7 自愈回退机制

当交叉验证阶段发现高严重度问题的置信度低于阈值时，触发自愈回退——将问题及上下文反馈给 LLM Agent，请求重新审查。最多回退 3 轮，每轮回退时缩小审查范围（仅针对问题代码块）并提高 Prompt 的严格性。回退轮次由编排层条件边控制（见 3.9 流水线装配），每轮消耗独立计入 token 预算。

#### 3.9 流水线装配（LangGraph.js 编排）

编排层采用 LangGraph.js（`@langchain/langgraph`）的 StateGraph：共享状态以 Channel/Reducer 声明，节点返回增量更新，条件边与并行分支由图结构表达，业务流程一目了然。

```typescript
// packages/core/src/state.ts —— 共享状态定义（Channel/Reducer 模型）
import { Annotation } from '@langchain/langgraph';
import type { CodeContext, Finding, ReviewMetrics, ReviewPlan } from '@ai-review/shared';

const FindingList = Annotation<Finding[]>({
  reducer: (current, patch) => dedupeFindings([...current, ...patch]), // 并行分支结果自动合并去重
  default: () => [],
});

export const ReviewState = Annotation.Root({
  context: Annotation<CodeContext>({ reducer: (_, b) => b, default: () => emptyContext() }),
  plan: Annotation<ReviewPlan>({ reducer: (_, b) => b, default: () => emptyPlan() }),
  findings: FindingList,
  healRounds: Annotation<number>({ reducer: (_, b) => b, default: () => 0 }),
  metrics: Annotation<ReviewMetrics>({ reducer: (_, b) => b, default: () => emptyMetrics() }),
});
```

```typescript
// packages/core/src/pipeline.ts —— LangGraph 流水线装配
import { StateGraph, START, END, MemorySaver } from '@langchain/langgraph';
// 团队版持久化（可审计/断点恢复）：
// import { SqliteSaver } from "@langchain/langgraph-checkpoint-sqlite";

function routeAfterValidate(s: ReviewState): 'heal' | typeof END {
  const needsHeal = s.findings.some((f) => f.severity === 'BLOCKER' && f.confidence < 0.6);
  return needsHeal && s.healRounds < 3 ? 'heal' : END;
}

export function buildPipeline() {
  return new StateGraph(ReviewState)
    .addNode('parse', parseDiffNode) // Diff 解析 + 上下文包构建
    .addNode('plan', riskPlanNode) // 风险规划分流
    .addNode('correctness', correctnessNode) // 三条并行审查分支
    .addNode('security', securityNode)
    .addNode('performance', performanceNode)
    .addNode('validate', crossValidateNode) // 交叉验证 + 幻觉抑制
    .addNode('heal', selfHealNode) // 自愈回退（条件进入）
    .addNode('report', reportNode) // 报告组装、落库、推送
    .addEdge(START, 'parse')
    .addEdge('parse', 'plan')
    .addEdge('plan', ['correctness', 'security', 'performance']) // fan-out：三路并行
    .addEdge('correctness', 'validate') // fan-in：汇聚点等待全部分支完成
    .addEdge('security', 'validate')
    .addEdge('performance', 'validate')
    .addConditionalEdges('validate', routeAfterValidate)
    .addEdge('heal', 'validate')
    .addEdge('report', END)
    .compile({ checkpointer: new MemorySaver() }); // 开发用内存快照，团队版换 SQLite/Postgres Saver
}

// 执行：thread_id = 审查 ID；每个 superstep 后 checkpoint 保存一次状态快照
const app = buildPipeline();
for await (const update of app.stream(initialState, {
  configurable: { thread_id: reviewId },
  streamMode: 'updates', // 节点级增量事件
})) {
  publishToSSE(reviewId, update); // 直通 API Server 的 SSE → Dashboard 实时进度
}
```

**编排层设计要点**：

- **并行审查即 fan-out/fan-in**：`plan → [correctness, security, performance]` 三路并行由图结构表达，LangGraph 的 superstep 模型保证汇聚点等待全部分支完成；发现结果经 `findings` reducer 自动合并去重，无需手写 Promise.all。
- **条件边 = 自愈回退**：`routeAfterValidate` 精确对应 3.0 的业务规则（BLOCKER 置信度 < 0.6 且 healRounds < 3 → heal），业务规则与图结构一一对应。
- **checkpoint 可审计**：checkpointer 在每个节点后保存状态快照，审查中断可从断点恢复、完整执行轨迹可回放，直接兑现"可审计原则"；团队版切换 SqliteSaver/PostgresSaver 即可持久化。
- **流式事件直通 Dashboard**：`graph.stream()` 的节点级更新经 SSE 透传，3.10 的实时进度条无需额外事件总线。
- **人机协同扩展点**：LangGraph 的 `interrupt()` 可在关键节点（如 BLOCKER 处置）暂停等待人工决策，为 Phase 4 的"人工复核工作流"预留能力。
- **全局取消**：取消信号经 `app.invoke(..., { signal })` 传入并传播到所有运行中节点，Ctrl-C 立即中断所有 LLM 请求。

#### 3.11 使用入口设计（Web 优先）

系统不提供命令行入口。全部能力经 Web Dashboard 与 HTTP API 暴露，Git Hook 与 CI 复用同一个同步审查端点：

| 入口         | 触发方式                                                                    | 说明                                            |
| ------------ | --------------------------------------------------------------------------- | ----------------------------------------------- |
| Web 发起审查 | `POST /api/reviews` + SSE                                                   | 四种范围：暂存区 / 工作区 / 单个提交 / 提交区间 |
| Git Hook     | `git commit` → `.husky/pre-commit` → Node 运行器 → `POST /api/hooks/review` | 由管理后台一键安装并注入令牌                    |
| CI           | PR 触发 → `POST /api/hooks/review`                                          | 与 Hook 共用退出码契约                          |
| MCP          | `POST /api/mcp`（Streamable HTTP，默认关闭）                                | 静态分析工具对外开放                            |

**为什么移除 CLI**：CLI、Web、CI 三入口曾各自维护一套装配逻辑（配置加载、Provider 链、报告写盘），
规则与退出码语义容易漂移；且 `init` / `index` / `install-hook` 在 Web 上已有等价能力，
保留 CLI 只是让用户被迫回到终端。现在三条入口共用 `ReviewService` + `ReviewSource`，
"审查哪一份 diff""什么算阻断"只有一处定义。

**审查范围**（`ReviewSource`，定义于 `packages/shared/src/review-source.ts`）：

| target     | git diff 参数       | 新侧内容来源                   |
| ---------- | ------------------- | ------------------------------ |
| `staged`   | `--cached`          | `git show :path`（index blob） |
| `worktree` | 无（HEAD ↔ 工作区） | 磁盘文件                       |
| `commit`   | `<sha>^!`           | `git show <sha>:path`          |
| `range`    | `base...head`       | `git show <head>:path`         |

git 引用经白名单校验（首字符不得为 `-`，拒绝空白与控制字符），防止参数注入。

**退出码契约**（脚本与 CI 依赖的稳定接口，`packages/shared/src/exit-codes.ts`）：

| 退出码 | 含义                                          |
| ------ | --------------------------------------------- |
| 0      | 审查通过（或无发现超过阻断阈值）              |
| 1      | 存在 ≥ blockOn 级别的发现，阻断提交           |
| 2      | 配置/环境错误（配置校验失败、git 仓库无效等） |
| 3      | 审查超时或被取消（不阻断提交）                |

#### 5.1 Git Hook 集成

系统以 `pre-commit` hook 方式集成到 Vibe Coding 工作流中，在开发者执行 `git commit` 时自动触发。

**方案 A：Husky v9（Node.js 生态推荐）**：

```bash

```

```bash
# .husky/pre-commit（由管理后台「Git Hook 与 CI」写入，无需手工创建）
#!/bin/sh

```

运行器脚本（`.ai-review/hooks/pre-commit.mjs`）从 `.ai-review-cache/hook-token` 读取 Bearer 令牌，
`POST /api/hooks/review` 并按其 `exitCode` 放行或阻断；服务不可达时返回 3，不阻断本地提交。

**方案 B：CI 直接调用同一端点**（GitHub Actions）：

```yaml
- name: AI Review
  run: |
    set +e
    curl -sS -X POST "$AI_REVIEW_SERVER/api/hooks/review" \
      -H "authorization: Bearer $AI_REVIEW_TOKEN" \
      -H "content-type: application/json" \
      -d '{"repoPath":"'"$PWD"'","target":"range","base":"origin/main","mode":"full"}' \
      -o review.json
    exit_code=$(node -p "require('./review.json').exitCode")
    cat review.json
    exit $exit_code
```

> **Windows 兼容说明**：hook 入口是 POSIX sh（husky v9 经 `core.hooksPath` 在 Git Bash 下执行），
> 但真正的审查调用在 Node 运行器里，不依赖平台 shell；所有 git 调用均经 `execFile` 传参数组。

**慢审查不阻塞提交**：pre-commit 默认只跑 fast 模式；完整深度审查交给 CI（PR 触发）或 Dashboard 手动触发，两者结果在 Dashboard 中关联展示。

### 二、项目背景与问题定义

#### 2.1 Vibe Coding 时代的代码审查挑战

Vibe Coding 改变了代码的生产方式——AI 生成代码的速度远超人工编写，但生成代码的质量参差不齐。开发者需要一种与 AI 生成速度匹配的审查机制。传统的代码审查流程（发起 PR → 等待人工审查 → 修改 → 重新审查）在 AI 辅助开发场景下成为瓶颈。

与此同时，GenAI 代码审查工具虽然已经成熟，但在以下方面仍需改进：

- 幻觉率平均 18%，部分工具高达 27%
- 对业务逻辑漏洞的检测能力弱（平均召回率 21%）
- 缺乏项目特定上下文的注入能力

#### 2.2 现有方案的不足

| 方案类型    | 代表工具               | 不足                                     |
| ----------- | ---------------------- | ---------------------------------------- |
| 纯静态分析  | SonarQube, CodeQL      | F1 分数低（0.26-0.55），无法理解业务语义 |
| 纯 LLM 审查 | Copilot Code Review    | 幻觉率高，缺乏确定性验证                 |

| 开源工具    | ai-code-review-toolkit | 功能单一，缺乏多 Agent 协作和 RAG 集成   |

本项目的差异化定位：**开源、本地优先、全栈 TypeScript（pnpm Monorepo 单仓交付）、多 Agent 混合分析、深度集成 Vibe Coding 工作流**。

#### 3.1 ReAct Agent 循环的实现

基于 Vercel AI SDK 5 实现 ReAct 循环：Provider 抽象、工具调用循环、usage 统计由 SDK 承担，审查编排逻辑保留在自有代码中，兼顾开发效率与可控性：

```typescript
// packages/agents/src/review-agent.ts
import { generateText, stepCountIs } from 'ai';
import type { LanguageModel } from 'ai';
import type { CodeContext, Finding, ToolRegistry, TokenBudget } from '@ai-review/shared';

export class ReviewAgent {
  constructor(
    private readonly model: LanguageModel,
    private readonly tools: ToolRegistry, // 进程内注册表 + MCP 双通道
    private readonly systemPrompt: string,
    private readonly opts: {
      maxSteps?: number; // ReAct 最大步数
      signal?: AbortSignal; // 全局取消
      budget?: TokenBudget; // token 硬预算
    } = {},
  ) {}

  async review(context: CodeContext): Promise<Finding[]> {
    const { text, usage } = await generateText({
      model: this.model,
      system: this.systemPrompt,
      prompt: buildReviewPrompt(context), // 注入 diff + 函数级片段 + RAG 上下文
      tools: this.tools.toAISdkTools(), // 工具 → AI SDK tool()（zod 入参）
      stopWhen: stepCountIs(this.opts.maxSteps ?? 10),
      abortSignal: this.opts.signal,
      temperature: 0.1, // 低温度保证审查一致性
    });

    this.opts.budget?.account(usage);

    // 结构化校验：文件存在、行号落在 diff 范围内、字段类型正确；
    // 校验失败的输出不静默丢弃，而是触发自愈回退重新生成
    return parseFindings(text, context);
  }
}
```

#### 3.2 LLM Provider 抽象与降级链

为保证 pre-commit 不因云服务故障而阻塞开发者，Provider 层实现"云端主力 + 本地兜底"的降级链。

> **国内厂商接入约定**：DeepSeek、智谱 GLM、Moonshot Kimi、通义千问、豆包、MiniMax 与 OpenAI/Ollama 一样提供 OpenAI 兼容 `chat/completions` 端点，经 `packages/llm` 的同一套请求路径（`Bearer` 认证）接入，无需协议分支。各厂商的默认端点、`AI_REVIEW_<PROVIDER>_BASE_URL` 覆盖变量与推荐模型统一维护在 `packages/shared` 的 `model-catalog` 单一目录，`config-schema` 的 provider 枚举与后台页面选项均引用同一来源，避免双份维护。

```typescript
// packages/llm/src/provider.ts
import { createAnthropic } from '@ai-sdk/anthropic';
import { createOpenAI } from '@ai-sdk/openai';

export function buildModelChain(cfg: AiReviewConfig) {
  const anthropic = createAnthropic({ apiKey: resolveApiKey(cfg) });
  // Ollama 提供 OpenAI 兼容端点，同一套 AI SDK 代码即可接入本地模型
  const local = createOpenAI({
    baseURL: 'http://127.0.0.1:11434/v1',
    apiKey: 'ollama',
  });

  const primary = anthropic(cfg.llm.model);
  const fallback = local('qwen3-coder:30b');

  // 主模型超时/限流/5xx 时自动降级到本地模型（AI SDK middleware 实现，简化示意）
  return withFallback(primary, fallback, { retries: 2, timeoutMs: 30_000 });
}
```

成本策略与降级链呼应：高风险文件走云端主力模型，低风险文件在预算紧张或离线场景下降级到本地模型，极端情况（本地模型也不可用）仅运行静态分析并在报告中明确标注"本次未经 LLM 审查"。

### 四、测试与验证方案

#### 4.1 测试策略

**单元测试（Vitest）**：对 Diff 解析器、风险规划器、复杂度分析器、报告生成器、zod 配置校验等模块进行单元测试，覆盖边界条件（空 diff、二进制文件、超大文件、CRLF/中文路径——Windows 场景重点）。Vitest 与 Vite 8 共享 transform 管线，`packages/*` 的测试在 Turborepo 中并行调度。

**集成测试**：使用预置的代码仓库快照（含正常/异常分支 fixture），在临时目录中执行真实 git 操作（`git init` → `git add` → 触发流水线），端到端验证从 staged diff 到报告生成与退出码的完整链路。LLM 调用以**录制/回放**模式替换（首次真实调用时持久化响应为 fixture，此后回放），保证测试确定性且零 token 消耗。

**前端测试**：组件用 Vitest + Testing Library；API mock 用 MSW；Dashboard 关键路径（查看报告、标记误报）用 Playwright 做冒烟 E2E。

**基准测试**：构建包含已知缺陷的代码测试集（参考 CWE 分类），测量召回率、精确率和 F1 分数。测试集覆盖：

- 注入类：SQL 注入、命令注入、XSS（CWE-89/78/79）
- 认证类：缺失权限校验、硬编码凭证（CWE-287/798）
- 反序列化：不安全 pickle/eval（CWE-502）
- 业务逻辑：权限绕过、竞态条件

### 八、后续演进方向

1. **Vibe Coding 深度集成**：与 Cursor、Claude Code 等工具的深度联动，在 AI 生成代码后立即触发审查，实现"生成即审查"；工具总线经 MCP 对外开放后，Claude Code 可直接复用本系统的静态分析能力。
2. **强化学习优化**：基于开发者对审查发现的反馈（Dashboard 误报标记、采纳/拒绝），持续优化置信度模型与风险规划器权重。
3. **多仓库知识共享**：在团队或组织范围内共享 RAG 知识库，使一个项目学到的最佳实践惠及所有项目。
4. **形式化验证集成**：将 LLM 审查与轻量级形式化验证结合，对关键路径（如认证、支付）进行数学级正确性证明。
5. **自然语言审查规则**：允许开发者用自然语言定义审查规则（如"所有 API 必须返回统一的错误格式"），系统自动转化为可执行的检查逻辑。
6. **TS 7 原生编译器跟进**：随 TypeScript 7（tsgo）正式发布，将 typecheck/AST 分析迁移到原生编译器 API，获得数量级提速，进一步压缩审查延迟。
