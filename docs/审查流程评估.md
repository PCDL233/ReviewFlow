# 审查流程评估：现状、缺口与修复

本文对照「常规代码审查」（Conventional Code Review）的通行做法，逐步梳理本项目的审查链路，
列出偏离项与修复状态。评估基准为本次改造前的实现（`apps/cli` + `apps/server` + `packages/*`）。

## 一、当前审查链路的逐步梳理

```text
触发 → 读取 diff → 过滤 → 上下文构建 → 风险规划 → 并行审查 → 交叉验证 → 自愈 → 报告 → 落库/推送 → 人工处置
```

| #   | 环节       | 输入                                         | 输出                                    | 失败语义                             |
| --- | ---------- | -------------------------------------------- | --------------------------------------- | ------------------------------------ |
| 1   | 触发       | pre-commit（CLI）/ CI（`--base`）/ Web 手动  | 审查任务                                | 配置错误 → 退出码 2                  |
| 2   | 读取 diff  | `git diff --cached` / `git diff base...HEAD` | unified diff                            | git 错误上抛                         |
| 3   | 过滤       | diff + `review.ignorePatterns`               | 有效文件 diff                           | 二进制/空白/忽略文件静默丢弃         |
| 4   | 上下文构建 | 文件 diff + RAG                              | `FileContext[]`（AST 片段、签名、召回） | 解析失败降级为行级窗口               |
| 5   | 风险规划   | 文件 diff + 文件热度                         | `deep / quick / staticOnly`             | 无失败路径（纯确定性）               |
| 6   | 并行审查   | 上下文 + Provider                            | `Finding[]`                             | Provider 降级链 云端 → Ollama → mock |
| 7   | 交叉验证   | 全部 findings                                | 重定级/重算置信度/去重排序              | 无失败路径                           |
| 8   | 自愈       | 低置信度 BLOCKER                             | 重审后的 findings                       | 最多 3 轮                            |
| 9   | 报告       | 流水线状态                                   | 五段式 Markdown/JSON/HTML               | 模板渲染，无 LLM 参与                |
| 10  | 落库/推送  | 报告 + diff                                  | SQLite 行 + SSE 事件                    | 落库失败 → failed 事件               |
| 11  | 人工处置   | 报告                                         | 误报标记 / 重跑 / 删除                  | 404（越权统一按不存在）              |

## 二、与常规代码审查的对照

| 维度             | 常规做法                           | 改造前实现                                                                 | 结论                   |
| ---------------- | ---------------------------------- | -------------------------------------------------------------------------- | ---------------------- |
| 审查对象的确定性 | 明确"审查哪一次提交/哪个区间"      | 只能审查暂存区或 CI 的 `base...HEAD`；Web 端无区间能力                     | ❌ 缺失                |
| 结论可追溯       | 报告绑定 commit SHA + 作者         | `ReviewMeta` 有 `commitHash/author` 字段但**从未填充**，DB 列恒为 NULL     | ❌ 缺失                |
| 审查范围可控     | 支持按提交回溯、按区间把关         | 无单提交审查                                                               | ❌ 缺失                |
| 规则可见可改     | 规则与阈值在系统内可查可改         | 已有自定义规则 + 阈值，但 `review.dimensions` **UI 可改而代码从不读取**    | ⚠️ 部分                |
| 严重度分级       | BLOCKER / WARNING / NIT 可配置阈值 | 已有，且阈值落到阻断判定                                                   | ✅                     |
| 阻断语义         | 阻断后明确"不许合并/提交"          | 退出码 0/1/2/3 契约清晰                                                    | ✅                     |
| 误报闭环         | 可标记误报并回流                   | 已支持 `isFalsePositive` 落库                                              | ✅（尚未用于模型调优） |
| 报告格式配置     | 格式可选                           | `report.format` / `includePraise` **从未被消费**                           | ❌ 缺失                |
| 大变更保护       | 单次审查有规模上限                 | 无文件数/行数上限，大提交可能耗尽预算与时间                                | ❌ 缺失                |
| 并发与配额       | 有并发上限与预算                   | 已有信号量 + `TokenBudget`；但自愈节点**绕过预算**且用无上限 `Promise.all` | ⚠️ 缺陷                |
| 人工审查交接     | 审查结果可导出、可分享             | 支持 Markdown/HTML/JSON 导出                                               | ✅                     |
| 路径安全         | 只允许访问授权仓库                 | 仅字符串前缀比较，**未解析符号链接**                                       | ⚠️ 缺陷                |
| 使用入口一致     | 一套规则、多个入口                 | CLI / Web / CI 三入口，Web 缺能力，规则实现分散                            | ⚠️ 分裂                |

## 四、修复矩阵与遗留技术债

**本轮已修复**：1、2、3、4、5、6、7、8、9、12。

**遗留技术债**（不阻塞当前流程，但影响审查质量上限）：

1. **交叉验证阶段 3（跨文件分析）**：需要 ts-morph 的编译级核对（签名变更 → 调用方未更新）。
   当前仅做文件内重定级，跨文件破坏性变更只能靠 LLM 语义判断，误报率更高。
2. **交叉验证阶段 4（自动修复建议）**：计划复用 ESLint 规则元数据生成 patch。当前 `suggestion`
   完全来自 LLM，质量不稳定。
3. **自愈"逐轮收窄"**：文档描述每轮缩小范围，实现是同一批文件重审 3 轮。
   若改为按 hunk 收窄，需要 `FileContext` 携带行级窗口。
4. **误报数据未回流**：`is_false_positive` 已落库，但尚未用于调整置信度基线或缓存失效策略。
5. **评价基准缺失**：没有"已知缺陷注入 → 检出率"的回归集，无法量化需求 3 提到的审查质量。
   `packages/core/test/benchmark.test.ts` 只覆盖性能，不覆盖检出质量。

## 五、改造后的目标流程

```text
                ┌─ Web：选仓库 → 选范围（暂存区/工作区/提交/区间）→ 实时进度 → 报告
触发 ───────────┼─ Hook：git commit → .husky/pre-commit → node 运行器 → POST /api/hooks/review
                └─ CI：PR → curl POST /api/hooks/review (range) → exitCode 决定是否阻塞

POST /api/{reviews,hooks/review}
   → toReviewSource()（参数完整性校验）
   → assertRepoPathAllowed()（realpath 白名单）
   → ReviewService.startReview({ repoPath, mode, source, blockOn })
       → pipeline: parse(单次 diff) → riskPlan(规模上限 + 预算) → fan-out(按 dimensions)
                   → validate → heal(预算受限) → report
       → buildReport(): commitHash / author / 截断说明
       → saveReport(): 记录 target + source_label（供 rerun 复现）
   → Web: 202 + SSE；Hook/CI: 同步等待 → exitCode 0/1/2/3
```

关键收口点：

- **一处 diff 来源定义**：`packages/diff/src/git-reader.ts` 的 `resolveSource`，
  Web / Hook / CI 全部经它，不可能出现"某个入口读错范围"。
- **一处退出码定义**：`packages/shared/src/exit-codes.ts`，Hook 运行器与 CI 步骤都读同一个值。
- **一处阻断判定**：`severityMeetsThreshold`，SSE 实时事件、落库状态、Hook 响应三者同口径。
